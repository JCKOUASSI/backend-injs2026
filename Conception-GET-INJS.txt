PARTIE 1 — PRÉSENTATION
--------------------------------------------------------------------------------

1.1 Objectifs

GET INJS APP prépare, simule, génère, contrôle, versionne, publie et consulte
les emplois du temps de l'INJS d'Abidjan pour une année académique donnée, à
partir de la chaîne LMD officielle (formation → parcours → niveau → semestre →
groupe → maquette → UE → ECUE → affectation → séance → EDT publié) et, lorsque
les étudiants n'ont pas de parcours dans l'application, à partir d'un fichier
d'inscrits importé (CSV / XLSX).

1.2 Périmètre retenu

- Institution : INJS d'Abidjan uniquement. Aucune référence SYGEP / CPFAE.
- 8 filières F01–F08 ; Licence S1–S6 et Master S7–S10 ; 30 ECTS/semestre,
  60 ECTS/niveau.
- Aucune table « Promotion » : le groupe (année + formation + parcours + niveau
  + vague + nom) porte la promotion — arbitrage déjà consigné dans le dépôt.
- L'import externe ne crée JAMAIS d'inscription administrative validée, de
  décision de jury ni de parcours académique officiel : il crée des
  `InscriptionImportee`, identifiables et supprimables.

1.3 Architecture retenue

  Backend  Django 5.1 + DRF, application `edts` (module GET-INJS)
  Frontend React 18 + Vite + React Router + Bootstrap (stack existante)
  Base     PostgreSQL en production, SQLite en développement/tests
  Moteur   `edts/moteur` : besoins → génération (backtracking) → validation →
           publication → orchestration annuelle → import des inscrits

Le module a été intégré à l'application Django E X I S T A N T E (`edts`), pas
dans un second backend. Aucune dépendance nouvelle n'a été introduite.

2.2 Éléments métier extraits

  (a) Chaîne canonique (doc 2 et 4) :
      Formation → Parcours → Promotion → Groupe → Maquette → UE → ECUE →
      Affectation pédagogique → Créneaux → Salles → Séances → EDT → Publication
      → Présences.   → Implémenté tel quel (edts/models.py, moteur/besoins*.py).

  (b) Contraintes absolues (doc 2, §10 "J") :
      - un enseignant ne peut pas assurer deux séances simultanément (C1) ;
      - un groupe ne peut pas suivre deux séances simultanément (C2) ;
      - une salle ne peut pas accueillir deux séances simultanément (C3) ;
      - effectif ≤ capacité de la salle (C4) ;
      - un TP exige une salle spécialisée (compatibilité) (C7).
      → Implémenté : contraintes.py (C1…C9), generation.py, validation.py.

  (c) Contraintes souples avec pénalité (doc 2, §11 "K") :
      éviter > 4 h consécutives, éviter les trous, éviter 8 h/jour, respecter
      les préférences enseignants, équilibrer les matières, éviter les salles
      surdimensionnées.
      → Implémenté en deux registres :
        (1) toujours actives : préférences enseignants (poids 2) et salle
            surdimensionnée (poids 1) ;
        (2) configurables et INACTIVES PAR DÉFAUT : trous, séries de plus de
            N heures consécutives, journées de plus de N heures. Aucune
            pondération officielle n'étant fournie par les documents, ces
            règles ne s'appliquent que sur décision explicite de l'INJS
            (réglage Django `EDTS_CONTRAINTES_SOUPLES` → voir §5.7 bis).
            Voir `edts/moteur/contraintes.py` (bloc « Contraintes SOUPLES »).

  (d) Canevas horaire officiel (Excel, feuille « 13. Emploi du temps (modèle) ») :
      6 jours (lundi → samedi) × 4 plages : 07h30–09h30, 09h45–11h45,
      13h30–15h30, 15h45–17h45 = 24 créneaux de 2 h.
      → Vérifié en base : les 24 CreneauTemplate enregistrés correspondent
        EXACTEMENT à cette grille (aucun créneau inventé).

  (e) Volumes horaires (doc 2, §C/§D) : un ECUE porte CM + TD (ex. 20 h CM +
      10 h TD) découpés en séances de 2 h → 10 séances CM + 5 séances TD.
      → Implémenté : besoins.py / besoins_maquette.py calculent le nombre de
        séances à partir des volumes réels ; aucune séance n'est inventée.

  (f) Infrastructures (docs 5 et 8) : 43 salles de cours, 2 blocs pédagogiques,
      amphithéâtres ENSEPS/ENSEP, gymnases, terrains ; l'ambition est de gérer
      plus de 250 espaces.
      → Modèle prêt (RefSite, RefBatiment, RefSalle avec type_lieu et capacité).
        IMPORTANT : les salles réelles ne sont PAS saisies (décision métier :
        ne pas inventer un patrimoine officiel).

3.4 Cycle de vie d'une campagne

  BROUILLON → VALIDATION_DONNEES → PRET → EN_COURS
            → TERMINE | TERMINE_AVEC_ANOMALIES | ECHEC
            → VALIDE → PUBLIE

  Transitions autorisées uniquement (table TRANSITIONS). Une campagne PUBLIEE
  est figée : on crée une nouvelle campagne pour un nouveau cycle.
  Relance possible depuis TERMINE / TERMINE_AVEC_ANOMALIES / ECHEC.

3.5 Concurrence et reprise

  - `demarrer_campagne` ouvre une transaction, prend un verrou pessimiste
    (select_for_update) sur la campagne, refuse si statut == EN_COURS
    (`CAMPAGNE_DEJA_EN_COURS`, HTTP 409) puis crée l'exécution.
  - L'exécution tourne dans un fil d'arrière-plan (`threading.Thread`,
    daemon) quand `asynchrone=true` ; `asynchrone=false` exécute dans la
    requête (tests, petits périmètres). Aucun service externe requis (pas de
    Celery dans le dépôt) : l'absence de broker n'empêche pas le fonctionnement.
  - Chaque exécution est journalisée, y compris les échecs (`ExecutionCampagne.
    erreur`), ce qui permet de reprendre en connaissant la cause.

3.6 API (routes ajoutées, toutes sous /api/edts/campagnes/)

  GET    /campagnes/                    lecture (tout authentifié)
  POST   /campagnes/                    création (planification)
  GET    /campagnes/<pk>/               lecture
  POST   /campagnes/<pk>/demarrer/      lancement (planification), 202 si async
  GET    /campagnes/<pk>/statut/        interrogation périodique
  GET    /campagnes/<pk>/resultat/      bilan par groupe + anomalies + historique
  POST   /campagnes/<pk>/donnees-pretes/ BROUILLON → PRET (planification)

  (409), TRANSITION_REFUSEE (409), VALIDATION_BLOQUANTE (409),
  PUBLICATION_INCOMPLETE (409), AUCUN_EDT_A_VALIDER/A_PUBLIER (409).

3.7 Algorithme de génération

  1. Besoins : AffectationPedagogique quand elle existe ; sinon maquette active
     (CM/TD/TP → nombre de séances de 2 h).
  2. Contexte : créneaux officiels, salles actives, semaines, index de
     disponibilités, index d'occupations.
  3. Backtracking chronologique borné par un budget de placements : à chaque
     étape, le besoin le plus contraint, candidats triés par (score de
     pénalités, jour, heure, salle).
  4. Validation : C1…C9 + couverture des besoins ; toute violation est listée.
  5. Persistance : un EDT BROUILLON par groupe (transaction par EDT).
  6. Publication : geste humain, après validation, atomique pour un périmètre de
     campagne.

  Garanties : déterministe à paramètres égaux (tri stable), aucune séance
  inventée, aucun placement en conflit, échec explicite plutôt que plan faux.

3.8 Gestion des étudiants importés

  Fichier CSV (séparateur « ; » ou « , ») ou XLSX, taille maximale 20 Mo,
  colonnes reconnues par synonymes (matricule, nom, prénoms, sexe, formation,
  filière, parcours, niveau, semestre, groupe, vague). Clé d'idempotence :
  (année académique, matricule). Analyse SANS écriture puis import réel.
  Stockage : `InscriptionImportee` (fichier, empreinte SHA-256, ligne source).
  Aucun étudiant, aucune inscription administrative, aucun parcours créé.

3.9 Optimisations apportées (mesurées, Partie 6)

  - Disponibilités (C5/C6/préférences) : une requête par année au lieu d'une
    requête par candidat → `contraintes.indexer_disponibilites`.
  - Occupations (C1/C2/C3) : index (ressource, jour) maintenu par le solveur au
    lieu d'un parcours complet de la liste à chaque candidat →
    `contraintes.indexer_occupations` + ajouter/retirer.
  Résultat mesuré : 3 500 étudiants, 961 s → 8,8 s ; 7 000 étudiants, 350 s → 36,3 s.

3.10 Sécurité et habilitations

  - Réutilisation stricte de `edts.permissions` (aucun second RBAC) :
    planification pour créer/lancer, DIRECTION/ADMIN pour valider/publier,
    lecture pour tout compte authentifié.
  - Contrôle serveur sur chaque route (un bouton masqué n'est pas une
    protection) ; l'interface ne fait que refléter le droit.
  - Taille de fichier bornée, contenu validé, erreurs explicites.
  - Aucun secret dans ce document.

PARTIE 5 — GUIDE UTILISATEUR
--------------------------------------------------------------------------------

5.1 Créer une campagne
  Menu GET-INJS → « Campagnes de génération » (/edt/campagnes). Choisir l'année
  académique, saisir un libellé unique, indiquer les semaines, cocher
  « Enregistrer les EDT ». La création n'écrit aucun emploi du temps.

5.1 bis Vérifier les données avant de générer
  Menu GET-INJS → « Audit des données » (/edt/audit). L'écran interroge
  `/api/edts/lmd/audit/` et affiche chaque contrôle avec son niveau réel
  (OK / Avertissement / Bloquant), son code, son explication et l'action
  recommandée. Exemple observé en base de démonstration : BLOCKING
  `HORS_PERIMETRE_INJS` tant qu'aucune affectation pédagogique ne porte une
  formation INJS ; CANEVAS_HORAIRE_OK (14 créneaux types) ; RESSOURCES (7 salles).
  Le tableau des contraintes C1→C10, séparé des préférences, est rappelé dessous.

5.1 ter Versions & publication
  Menu GET-INJS → « Versions & publication » (/edt/versions). Liste réelle des
  EDT versionnés (`/api/edts/lmd/versions/`) avec statut, auteur de création,
  dates de validation et de publication, motif de modification. Pour la version
  sélectionnée, l'audit (`/api/edts/lmd/<id>/audit/`) affiche violations,
  avertissements et couverture ; « Valider » appelle
  `/api/edts/lmd/<id>/validate/`, « Publier » n'est actif qu'après validation.
  Un refus de validation est affiché comme un refus, avec le code de la
  contrainte violée.

5.2 Importer les inscrits
  Menu GET-INJS → « Génération annuelle & import » : sélectionner le fichier
  (CSV/XLSX), lancer « Analyser » (aucune écriture), lire le rapport (lignes
  rejetées avec motif, cohortes, effectifs), puis « Importer ».

5.3 Vérifier les données
  La synthèse affiche l'effectif réel importé par cohorte. Un groupe sans
  maquette ni affectation est signalé « non planifiable » — jamais complété
  par des données inventées.

5.4 Corriger les anomalies
  Deux causes dominantes : aucune maquette active pour la formation/niveau, ou
  emploi du temps déjà validé/publié. Corriger en Scolarité (maquette,
  affectations, groupes) puis relancer la campagne.

5.5 Générer
  Bouton « Générer › de la campagne. La génération tourne en arrière-plan ;
  l'écran interroge l'état réel toutes les 3 s (aucun pourcentage inventé).
  Le bilan par groupe indique séances attendues / placées / non placées et le
  motif d'échec éventuel.

5.6 Consulter les conflits
  Menu GET-INJS → « Conflits & contraintes » (source : /api/edts/conflits/),
  ou colonne « Motif » du bilan de campagne.

5.7 Modifier une séance
  Tableau des emplois du temps → grille : chaque séance porte deux actions.

  « Déplacer » (`/api/edts/lmd/items/<id>/move/`) : le serveur liste les
  positions qu'il a lui-même validées (créneau + salle), l'utilisateur en
  choisit une, puis le serveur revalide C1→C10 sur le plan complet et refuse
  en 409 avec le code de la contrainte violée. Si le plan existant est déjà en
  violation, l'écran affiche cette cause AVANT « aucune position » — un plan
  invalide bloque tout déplacement, et le dire évite un diagnostic faux.

  « Annuler » (`/api/edts/lmd/items/<id>/cancel/`) : motif obligatoire,
  désactivation logique (aucune suppression), journalisée et réversible via
  « Réactiver ». Sans motif : 400 MOTIF_ANNULATION_REQUIS. Sur un EDT publié
  ou archivé : 409 STATUT_EDT_INVALIDE.

5.7 bis Contraintes souples (activables, jamais bloquantes)
  Politique par défaut (`contraintes.SOUPLES_DEFAUT`), identique à un solveur
  sans règles souples tant qu'elle n'est pas activée :

    actives=False            aucune règle souple n'est évaluée
    max_heures_consecutives=4.0
    max_heures_par_jour=8.0
    tolerance_minutes=15     une interruption ≤ 15 min n'est pas un trou
    penaliser_trous=True     poids_trou=1
    poids_consecutif=2       poids_surcharge=3
    pause_dejeuner=None      aucune pause institutionnelle supposée

  Priorité de configuration : défauts < réglage Django
  `EDTS_CONTRAINTES_SOUPLES` < **ligne enregistrée dans l'admin** (voir
  §5.7 ter) < paramètre explicite de `generate_schedule()`
  (`contraintes_souples=`). Un réglage mal orthographié ou mal typé lève une
  erreur explicite : un `ValueError` plutôt qu'une règle silencieusement
  ignorée.

  Codes produits (pénalités, jamais des refus) :
    TROU_HORAIRE                     temps d'attente entre deux séances du
                                     groupe, hors tolérance et hors pause ;
    PLUS_DE_X_HEURES_CONSECUTIVES    série continue > max_heures_consecutives.
                                     La charge retenue est la SOMME des durées
                                     de cours de la série : une série
                                     09:00–11:00 + 11:15–13:00 vaut 4 h de
                                     cours et non 4 h 15 de présence ;
    SURCHARGE_JOURNALIERE            total du jour > max_heures_par_jour.

  Trois précisions de conception, assumées et testées :
    - les bornes sont jugées par JOURNÉE DE GROUPE (une journée peut être
      longue pour un enseignant sans l'être pour l'étudiant) ;
    - les seuils sont des DÉPASSEMENTS STRICTS : 4 h = pas de pénalité ;
    - `pause_dejeuner` vaut `None` par défaut. L'INJS n'ayant publié aucune
      pause officielle, le moteur n'en invente pas : sans pause déclarée
      (ex. `('12:15', '13:30')`), une coupure méridienne de 1 h 15 est
      signalée comme trou. C'est explicite, réglable et vérifié par un test
      dédié (avec et sans pause déclarée).

  Visibilité : `GET /api/edts/lmd/constraints/` renvoie
  `souples.politique`, `souples.origine`, `souples.reglage`,
  `actives_par_defaut: false`, l'explication, le moyen d'activation et les
  trois codes. Aucune règle ne s'applique sans être affichée. Le bilan de
  génération expose `metrics.contraintes_souples` (`active`, `trous`,
  `series_trop_longues`, `journees_surchargees`, `detail`).
  Les pauses sont stockées en minutes (unité interne du moteur) et rendues en
  « 12:15 – 13:30 » partout où un humain les lit (API, écrans).

5.7 ter Régler les contraintes souples depuis l'administration
  Admin Django › « GET-INJS – Politique des contraintes souples ».

  Pourquoi une table et pas seulement un réglage : `EDTS_CONTRAINTES_SOUPLES`
  ne s'applique qu'au déploiement. L'INJS ne peut donc pas décider seule qu'une
  journée de 9 h devient problématique — il faudrait modifier un fichier et
  redémarrer le service. La ligne unique `edts.PolitiqueContraintesSouples`
  (migration 0009) donne cette main au secrétariat / à la direction.

  Garanties :
    - **ligne unique** — `save()` force la clé primaire à 1 ; la seconde ligne
      est impossible, donc aucune ambiguïté sur les règles appliquées ;
    - **désactivée par défaut** — créer la ligne ne change rien tant que
      « actives » n'est pas coché ; le comportement historique est préservé ;
    - **non supprimable** — supprimer effacerait la trace de la décision ;
      l'admin refuse l'ajout d'une seconde ligne (403) et la suppression ;
    - **traçable** — auteur (`modifie_par`, renseigné par l'admin elle-même),
      date (`modifie_le`) et motif libre ; l'API expose ces trois champs ;
    - **validée** — pause incomplète ou inversée, borne nulle, poids nul sont
      refusés avec un message qui dit quoi corriger (un poids nul rendrait la
      pénalité invisible : pour ne pas appliquer une règle, on la désactive).

  Effet visible : l'écran « Audit des données » affiche la politique effective,
  son **origine** (« valeurs par défaut du code », « réglage de déploiement »,
  « réglage enregistré dans l'administration »), les bornes, la pause déclarée
  ou son absence, les poids, le motif et le dernier auteur. Un utilisateur peut
  donc toujours savoir qui a décidé quoi, et si la règle qu'il subit vient du
  code ou de son établissement.

5.8 Simuler une variante
  Générer avec « Enregistrer les EDT › décoché : le plan est produit et
  contrôlé sans être persisté ; les EDT officiels ne sont pas modifiés.

5.9 Valider une version
  Bouton « Valider » (DIRECTION/ADMIN). Le serveur revérifie chaque EDT ;
  si une contrainte obligatoire est violée, la validation est refusée avec la
  liste des violations.

5.10 Publier
  Bouton « Publier » après validation. Publication atomique : si un EDT du
  périmètre échoue, aucun n'est publié. L'historique de la campagne conserve
  date, auteur et motif.

5.11 Exporter
  Menu GET-INJS → « Export / Impression » (CSV : groupes, enseignements,
  étudiants, créneaux, affectations, indisponibilités) et export CSV / PDF
  depuis l'écran de l'emploi du temps (trois boutons : CSV, Excel, PDF).
  Le classeur Excel contient une feuille « Séances » (jour, horaires, semaines,
  nature, intitulé, UE, ECUE, enseignant, groupe, parcours, niveau, semestre,
  salle, capacité, formation, statut) avec en-têtes figés et filtre
  automatique, et une feuille « Synthèse » (métadonnées + décompte réel des
  lignes + filtres appliqués). Les filtres de l'URL (`groupe_id`, `salle_id`,
  `formation_id`, `enseignant_id`, `semaine`, `jour`) s'appliquent à l'export
  comme à l'écran, via la même fonction `_seances_filtrees`.
  Le PDF est une grille A4 paysage
  (colonnes = jours réellement occupés, lignes = plages réellement utilisées,
  cellules = intitulé, salle, enseignant, groupe), produite par le serveur à
  partir de la même grille que l'écran. Le paramètre `?semaine=N` filtre la
  semaine ; sans séance, le document l'indique.

PARTIE 8 — PROCÉDURE DE DÉPANNAGE
--------------------------------------------------------------------------------

Symptôme : « Aucune campagne pour cette année académique »
  Cause : aucune campagne créée. Action : en créer une (Partie 5.1).

Symptôme : HTTP 409 CAMPAGNE_DEJA_EN_COURS
  Cause : une exécution tourne déjà (fil d'arrière-plan). Action : attendre la
  fin (l'écran interroge l'état toutes les 3 s) ; si le processus serveur a été
  arrêté pendant l'exécution, la campagne reste EN_COURS : créer une nouvelle
  campagne ou repasser l'année en revue (aucune reprise automatique n'est
  inventée).

Symptôme : statut ECHEC avec motif AUCUN_GROUPE_INJS
  Cause : aucun groupe actif dans le périmètre INJS pour l'année.
  Action : importer les inscrits ou créer les groupes en Scolarité.

Symptôme : groupes « non planifiés », motif AUCUN_BESOIN_PLANIFIABLE
  Cause : ni affectation pédagogique, ni maquette active ne couvre la cohorte.
  Action : activer une maquette ou saisir les affectations, puis relancer.

Symptôme : validation refusée (VALIDATION_BLOQUANTE)
  Cause : un EDT contient une violation de contrainte obligatoire.
  Action : lire `detail.edt_en_echec[].violations`, corriger l'EDT, revalider.

Symptôme : publication refusée (PUBLICATION_INCOMPLETE)
  Cause : un EDT du périmètre n'a pas pu être publié. Aucun EDT du lot n'est
  publié (atomicité). Action : corriger l'EDT signalé puis republier.

Symptôme : import rejeté (motif MATRICULE_MANQUANT, NIVEAU_INCONNU…)
  Cause : donnée du fichier. Action : corriger le fichier ou le mapping.

Symptôme : fichier > 20 Mo
  Cause : limite de sécurité. Action : découper le fichier.

Symptôme : erreurs de migration
  Action : `makemigrations --check --dry-run` puis `migrate edts`. Ne jamais
  supprimer la base ni les migrations.

Symptôme : lenteur de génération
  Action : vérifier que les index sont actifs (disponibilités, occupations) ;
  mesurer avec `benchmark_getinjs`.

Symptôme : permissions (403)
  Cause : rôle hors planification (création/lancement) ou hors DIRECTION/ADMIN
  (validation/publication). Action : utiliser un compte habilité ; l'écran
  reflète le droit mais le serveur décide.

TLS : SSL_ERROR_SYSCALL).

Deux livrables permettent de l'exécuter dès qu'un SDK est disponible :

  arena/lancer-mobile.sh
      cherche le SDK dans .sdk/, extrait l'archive officielle si besoin,
      lance `flutter pub get` (avec repli `--offline` si .sdk/pub-cache
      existe), construit `flutter build web --dart-define=API_BASE_URL=`
      puis démarre le serveur.

  arena/serveur_mobile.py (port 3001)
      sert le build web ET relaie `/api/*` vers Django sur 127.0.0.1:8000.
      Le relais est nécessaire : le navigateur de l'utilisateur n'a pas accès
      au 127.0.0.1 du bac à sable. Comme `API_BASE_URL` est vide, l'application
      appelle `/api/...` sur sa propre origine : même origine → aucun CORS,
      aucune URL codée en dur.

Vérifié réellement (API + serveur de test) :
  GET  /                 → 200      GET  /assets/a.txt   → 200
  GET  /login (SPA)      → 200      GET  /api/edts/campagnes/ (avec jeton) → 200
  POST /api/auth/login/  → 200      GET  /api/auth/me/ (sans jeton)        → 401
  POST /api/edts/campagnes/ (avec jeton) → 201 (campagne créée puis supprimée)
  API arrêtée            → 502 + message explicite (jamais une page blanche)

NOT RUN : `flutter pub get`, `flutter build web`, `flutter test` et l'application
mobile elle-même — SDK absent. Le chemin SDK-absent du script est, lui, exécuté
et vérifié (message d'aide explicite, code de sortie 2).
