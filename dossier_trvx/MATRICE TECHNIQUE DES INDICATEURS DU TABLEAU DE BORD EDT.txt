Le document est prêt ci-dessous. Il constitue une première version technique structurée à partir du dossier INJS-EDT transmis en 17 parties, des analyses précédentes et des éléments identifiés dans le moteur EDT V2.

J’ai volontairement distingué les éléments confirmés dans le code des éléments qui nécessitent encore une vérification. L’objectif est d’éviter de construire un tableau de bord reposant sur des données fictives ou des calculs inexacts.

1. OBJECTIFS

La matrice technique doit permettre de construire un tableau de bord décisionnel capable de mesurer :

* La qualité de la programmation des emplois du temps.
* Le niveau de couverture des enseignements.
* La répartition des heures programmées.
* La réalisation effective des enseignements.
* La charge pédagogique des enseignants.
* L’utilisation des salles.
* Les annulations et reports.
* Les anomalies de programmation.
* Le respect des volumes horaires prévus dans les maquettes pédagogiques.

Le tableau de bord doit fournir une vision institutionnelle et permettre de descendre progressivement jusqu’à une séance particulière.

2.3. Point technique important : rattachement ECUE

La migration suivante a été identifiée :

edts.0012_affectationcreneau_ecue

Elle introduit le rattachement direct de l’ECUE sur AffectationCreneau.

Le contrat fonctionnel retenu est :

def ecue_de_seance(seance):
    """
    Déterminer l'ECUE réel d'une séance.
    """
    # 1. Priorité au rattachement direct
    if seance.ecue_id:
        return seance.ecue
    # 2. Solution de repli
    if seance.affectation_pedagogique:
        return seance.affectation_pedagogique.ecue
    # 3. Aucun rattachement valide
    return None

Ce code représente le contrat fonctionnel attendu, pas nécessairement l’implémentation littérale déjà présente.

Le système doit également :

* Vérifier la cohérence entre UE et ECUE.
* Vérifier la cohérence avec la formation.
* Détecter les rattachements contradictoires.
* Ne pas inventer un ECUE lorsque la relation est absente.

11. RÈGLES DE CALCUL TRANSVERSALES

11.1. Calcul des durées

Le moteur dispose des champs :

minute_debut
minute_fin

La durée en minutes est :

duree_minutes = minute_fin - minute_debut

Conversion en heures :

duree_heures = duree_minutes / 60

Il faut rejeter les durées nulles ou négatives.

11.2. Taux d’exécution

Formule :

Taux = \frac{Volume\ réalisé}{Volume\ prévu} \times 100

Exemple :

* Volume prévu : 120 heures.
* Volume réalisé : 90 heures.

Résultat :

Taux = \frac{90}{120}\times100=75\%

Si le volume prévu est nul, le taux doit être déclaré non calculable.

Il ne faut pas afficher automatiquement 100 %.

11.3. Volume restant

Volume\ restant = Volume\ prévu - Volume\ réalisé

Une valeur négative doit être signalée comme anomalie ou dépassement, et non masquée.

11.4. Prévention des doublons

La combinaison des éléments suivants doit être examinée pour identifier une occurrence :

* date_seance
* cle_occurrence_v2
* emploi_du_temps
* Identifiant du créneau.
* Révision du calendrier.

Le calcul ne doit pas additionner deux occurrences représentant la même séance.

20. DÉCISION ARCHITECTURALE

Je recommande de retenir les décisions suivantes pour le développement du tableau de bord.

Décision 1 — Une source de vérité unique

Les indicateurs doivent être calculés à partir des données Django et PostgreSQL existantes.

Décision 2 — Séparation programmation/réalisation

L’EDT représente une programmation. L’exécution représente une réalisation. Les deux ne doivent jamais être confondues.

Décision 3 — Respect de la hiérarchie pédagogique

Le rattachement Formation → UE → ECUE doit être fiable.

Décision 4 — Calcul centralisé

Les calculs doivent être regroupés dans des services Django réutilisables.

Décision 5 — Sécurité côté backend

Chaque API doit appliquer les autorisations correspondant au profil utilisateur.

Décision 6 — Historique préservé

Aucune modification destructive des données historiques.

Décision 7 — Transparence des données

Tout indicateur non calculable doit être signalé comme tel. Il ne faut pas remplacer une donnée manquante par une valeur arbitraire.

21. CONCLUSION ET VALIDATION

La matrice définit le socle technique du futur tableau de bord décisionnel EDT de l’INJS-LMD 2026.

Elle couvre les indicateurs institutionnels, pédagogiques, organisationnels et opérationnels.

Elle permet également de distinguer les données déjà identifiées dans le moteur EDT V2 de celles qui nécessitent encore un audit ciblé.

Ordre d’exécution recommandé

Je propose de commencer immédiatement par trois vérifications :

1. Audit du modèle de séance et du registre d’exécution : identifier définitivement comment une séance passe de programmée à réalisée.
2. Audit des volumes horaires des maquettes : identifier les sources officielles des heures prévues par UE et ECUE.
3. Audit des rattachements pédagogiques : contrôler la propagation Formation → UE → ECUE → Séance.

Ces trois vérifications conditionnent la fiabilité de presque tous les indicateurs.
