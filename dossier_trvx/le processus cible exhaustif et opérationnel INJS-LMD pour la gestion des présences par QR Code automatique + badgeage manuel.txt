Voici le processus cible exhaustif et opérationnel INJS-LMD pour la gestion des présences par QR Code automatique + badgeage manuel, avec géolocalisation et contrôle de présence des étudiants, enseignants et encadrants, en conservant l’architecture existante Django API 8000 + React 3000 + Flutter PWA, ainsi que le mécanisme QR → entrée/sortie → heartbeat GPS → sortie/fin de séance → historique.

2. Les trois populations concernées

Le système doit gérer trois catégories d’acteurs.

Population	QR	Entrée	Sortie	GPS	Heartbeat	Présence
Étudiant	Oui	Oui	Oui	Oui	Oui	Oui
Enseignant	Oui	Oui	Oui	Oui	Oui	Oui
Encadrant	Oui	Oui	Oui	Oui	Oui	Oui

Le moteur ne doit cependant pas traiter les trois populations comme identiques.

Étudiant

Le contrôle principal porte sur :

* appartenance au groupe ;
* inscription active ;
* présence à la séance ;
* position géographique ;
* heure de badgeage ;
* continuité de présence.

Enseignant

Le contrôle porte sur :

* affectation pédagogique ;
* séance concernée ;
* rôle d’enseignant ;
* position sur le site ;
* entrée ;
* continuité ;
* sortie.

Encadrant

Le contrôle porte sur :

* mission/activité affectée ;
* séance ou activité encadrée ;
* périmètre autorisé ;
* présence physique ;
* entrée/sortie ;
* historique.

⸻

3. Principe du QR Code

Le QR Code ne doit pas être considéré comme une simple image contenant :

ETUDIANT123

Le QR doit représenter une session de badgeage sécurisée et temporaire.

Architecture :

SÉANCE
   │
   ▼
SESSION QR
   │
   ├── identifiant
   ├── séance
   ├── expiration
   ├── statut
   ├── nonce/token
   └── règles de géolocalisation

Le QR est donc rattaché à :

Année
Formation
Parcours
Niveau
Semestre
Groupe
ECUE
Affectation pédagogique
Séance

8. Géolocalisation au badgeage

La géolocalisation doit être effectuée au moment du badgeage.

Données enregistrées :

latitude
longitude
accuracy
timestamp

Ne pas enregistrer uniquement :

"GPS = OK"

Il faut conserver la mesure permettant l’audit.

⸻

9. Geofence

Le site INJS doit disposer d’une zone géographique configurée.

SITE INJS
   │
   └── GEOFENCE
         │
         ├── latitude
         ├── longitude
         └── rayon

Le serveur calcule :

distance(position utilisateur, centre INJS)

Puis :

distance <= rayon
        │
        ├── OUI → géolocalisation acceptable
        │
        └── NON → hors périmètre

Important :

Le téléphone ne doit pas être l’autorité finale.

Le client fournit la position.

Le serveur décide.

Le système doit retourner un code explicite.

Exemples :

QR_INVALIDE
SEANCE_INACTIVE
SEANCE_TERMINEE
ETUDIANT_NON_INSCRIT

HORS_GEOFENCE
GPS_INDISPONIBLE
PRECISION_GPS_INSUFFISANTE
DEJA_BADGE
UTILISATEUR_NON_AUTORISE

Le frontend doit afficher une explication compréhensible.

Exemple :

Motif :
Vous êtes actuellement hors du périmètre
géographique autorisé pour cette séance.

12. Badgeage d’entrée

La présence doit distinguer au minimum :

ENTRÉE
SORTIE

Exemple :

09:58 → sortie

Le système peut alors calculer :

durée = sortie - entrée

13. Heartbeat GPS

Après une entrée validée :

ENTRÉE VALIDÉE
      │
      ▼
HEARTBEAT ACTIVÉ
      │
      ├── position
      ├── timestamp
      └── précision
      │
      ▼
API

Le heartbeat permet de contrôler que le participant reste présent pendant la séance.

Le mécanisme existant /api/scan/secure/heartbeat/ doit être conservé/intégré plutôt que remplacé.

15. Heartbeat et absence de GPS

Il faut distinguer :

GPS temporairement indisponible

WARNING

et :

Position durablement absente

ANOMALIE

Le système ne doit pas transformer automatiquement une perte ponctuelle du GPS en absence.

⸻

16. Fin automatique de séance

À la fin de la séance :

heure fin
   │
   ▼
fermeture QR
   │
   ▼
arrêt heartbeat
   │
   ▼
clôture présence

Si un étudiant n’a pas explicitement scanné la sortie, le système peut produire :

sortie automatique = fin de séance

mais le statut doit être différent d’une sortie QR explicite.

Exemple :

SORTIE_QR
SORTIE_AUTOMATIQUE_FIN_SEANCE

Cela garantit la traçabilité.

17. Badgeage manuel

Le badgeage manuel est un mécanisme exceptionnel et contrôlé.

Il ne doit pas être équivalent au QR automatique.

Architecture :

QR automatique
       │
       └── présence normale
Badgeage manuel
       │
       └── exception
              │
              ├── utilisateur autorisé
              ├── motif obligatoire
              ├── date/heure
              ├── auteur
              └── traçabilité

18. Qui peut forcer une présence ?

Uniquement les profils autorisés par RBAC.

Le système doit vérifier :

   ↓

   ↓

Il ne faut jamais accepter :

POST présence manuelle

simplement parce que l’utilisateur est authentifié.

28. Sécurité de la géolocalisation

Le serveur doit considérer les données GPS comme déclaratives jusqu’à validation.

Le client ne doit pas pouvoir envoyer :

{
  "inside_geofence": true
}

et être cru.

Il doit envoyer :

{
  "latitude": "...",
  "longitude": "...",
  "accuracy": "..."
}

Puis le serveur calcule lui-même :

distance
geofence
statut

29. Gestion de l’horodatage

Le serveur doit être l’autorité temporelle.

Ne pas faire confiance uniquement à :

heure du téléphone

Conserver :

server_timestamp
client_timestamp

si nécessaire à l’audit.

49. Cas réseau

Flutter doit pouvoir gérer :

GPS disponible
+
réseau temporairement indisponible

mais le serveur doit rester l’autorité finale.

Il faut éviter qu’un événement local soit présenté immédiatement comme une présence définitivement validée.

On distingue :

EN_ATTENTE_SYNCHRONISATION

puis :

VALIDÉ

ou :

REFUSÉ

après traitement serveur.

⸻

50. Cas batterie / application interrompue

Si Flutter est interrompu après l’entrée :

entrée enregistrée serveur
      ↓
heartbeat interrompu

Le système ne doit pas supprimer la présence.

Il doit produire éventuellement :

HEARTBEAT_INTERRUPTU

Puis appliquer la règle métier configurée pour déterminer le statut final.

Le Flutter Web/PWA ne doit pas être considéré comme capable de garantir un heartbeat natif en arrière-plan comme une application mobile native.

51. Confidentialité et minimisation

La géolocalisation étant une donnée sensible du dispositif opérationnel, le système doit appliquer :

* collecte uniquement lorsqu’elle est nécessaire à la présence ;
* accès selon RBAC ;
* journalisation des accès sensibles ;
* conservation selon politique INJS ;
* pas de suivi permanent hors activité/séance autorisée ;
* pas d’affichage public de coordonnées GPS ;
* séparation entre données opérationnelles et données d’audit.

Le principe fonctionnel est :

Pas de séance/activité
→ pas de tracking de présence
