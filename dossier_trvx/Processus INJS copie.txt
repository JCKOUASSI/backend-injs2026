CHAPITRE 1 — Création du compte
Statut d'implémentation : [PARTIEL]
================================================================================

1. Objectif
Permettre à un usager d'obtenir un compte authentifié (email + mot de passe) pour
accéder au portail selon son rôle. Aujourd'hui la création est principalement
administrative (seed / admin Django / API users) ; l'auto-inscription publique
n'est pas exposée sur le frontend.

2. Acteurs concernés
- Candidat / Étudiant (futur)
- Scolarité / Super Admin (création)
- Système (JWT, MFA optionnel)

3. Prérequis
- Email institutionnel ou personnel unique
- Politique de mot de passe respectée
- Groupe RBAC attribué (sinon rôle étudiant par défaut côté mapping UI)

4. Processus détaillé
Étape A — Création administrative (existant)
  1. Admin appelle POST /api/v1/auth/users/ ou utilise Django Admin / seed_injs_demo
  2. User créé avec email, noms, groupe, flags is_active
  3. Optionnel : must_change_password, enable_mfa

Étape B — Première connexion (existant)
  1. GET /login → saisie email/password
  2. POST /api/v1/auth/login/
  3. Si mfa_required → saisie TOTP → POST /api/v1/auth/mfa/verify/
  4. Stockage access/refresh tokens + user localStorage
  5. Redirection vers /{role} (etudiant|professeur|admin)

Étape C — Self-service (MANQUANT)
  - Formulaire public "Créer mon compte" lié à une campagne d'admission

5. Écrans concernés
- FE : /login (Login.jsx) — OK
- FE : aucun écran /register — MANQUANT
- API : POST /auth/login/, /auth/mfa/verify/, /auth/me/, CRUD /auth/users/

6. Données manipulées
User (email, password hash, first_name, last_name, groups, mfa_*, institution)
Tokens JWT access/refresh

7. Contrôles automatiques
- Email unique
- is_active=True requis pour login
- MFA si mfa_enabled
- Rafraîchissement token sur 401

8. Règles LMD
N/A (étape préalable au LMD)

9. Cas particuliers / exceptions
- Compte désactivé → 401
- MFA activé sans code → mfa_required
- Mauvais mot de passe → message "Aucun compte actif..." 

10. Notifications
Aucune notification automatique à la création (à prévoir : email de bienvenue).

11. Droits d'accès
Création users : niveaux ≤2 (admin/direction/responsables)
Login : public
Lecture /me : authentifié

12. Exemple concret INJS
etudiant1@demo.injs.ci / Demo@INJS2026! → rôle etudiant → /etudiant

13. Critères de validation (UAT / tests)
UAT-E1-01 : login admin OK
UAT-E1-02 : login étudiant OK et redirection /etudiant
UAT-E1-03 : mauvais password → erreur claire
UAT-E1-04 : MFA (si activé) bloque sans code

14. Insuffisances / à parfaire
MANQUANT : self-registration, vérification email, reset password UI, CGU.
À PARFAIRE : brancher hasPermission sur les écrans ; forcer must_change_password.
