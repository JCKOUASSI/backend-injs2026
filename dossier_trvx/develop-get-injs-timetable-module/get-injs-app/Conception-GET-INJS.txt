1. OBJET ET PERIMETRE
================================================================================

GET INJS APP est le module de gestion des emplois du temps de l'INJS d'Abidjan.
Il couvre :

  - les référentiels : filières (mentions), formations (parcours), maquettes LMD
    (modules/UE par semestre), bâtiments, salles, enseignants, vagues
    (promotions), groupes pédagogiques, années académiques ;
  - les populations : étudiants inscrits dans l'application de base OU importés
    depuis un fichier externe, avec reconstitution automatique du parcours ;
  - la génération des emplois du temps pour une année académique donnée, par
    filière, formation, niveau, groupe, vague et semestre, pour 3 500 à
    14 000 étudiants ;
  - l'exploitation : grille hebdomadaire imprimable, export CSV, historique
    des générations, journal des imports et indicateurs de couverture.

Deux situations fonctionnelles sont couvertes :

  SITUATION 1 — Les étudiants ont été inscrits via le processus LMD de
  backend-injs2026. Les groupes, vagues et semestres existent déjà. Il suffit
  de lancer la génération.

  SITUATION 2 — Un fichier externe contient tous les inscrits de l'année,
  éventuellement sans parcours académique (pas de groupe, pas de vague, pas de
  maquette). Le module :
    a) lit le fichier (CSV ou XLSX) et détecte les colonnes par alias ;
    b) normalise niveaux (L1..M2) et semestres (1..10) ;
    c) crée les filières, formations, vagues et groupes manquants ;
    d) génère une maquette LMD par défaut (8 modules par semestre) ;
    e) inscrit chaque étudiant sur les deux semestres de son niveau ;
    f) lance la génération des emplois du temps du périmètre importé.

permettre la génération sans bloquer la chaîne.

3. ARCHITECTURE TECHNIQUE RETENUE ET JUSTIFICATION
================================================================================

Le socle exécutable fourni pour cette mission est Next.js 16 (App Router),
React 19, PostgreSQL et Drizzle ORM. Le module a donc été implémenté dans ce
socle, avec une architecture en couches strictement équivalente au modèle
Django (API) + Flutter (frontend) demandé :

  Couche             Implémentation réelle              Équivalent cible
  --------------------------------------------------------------------------
  Domaine métier     get-injs-app/lib/*.ts              apps/timetable/domain
                     (pur TypeScript, testable)          (services Django)
  Persistance        src/db/schema.ts (Drizzle)          models Django
  API                src/app/api/**/route.ts            Django REST Framework
  Interface          src/app/**/page.tsx, composants    Flutter Web / mobile
  Données sources    get-injs-app/data/referentiel.ts    fixtures / JSON

Principes :
  - Le moteur de génération ne dépend ni du framework ni de la base : il reçoit
    des structures immuables et retourne des séances + statistiques + alertes.
    Il est donc réutilisable côté serveur, testable unitairement et portable
    vers un worker asynchrone.
  - Toute la logique d'import (parsing CSV/XLSX, alias, normalisation) est
    également hors framework.
  - Les services d'orchestration (src/lib/get-injs) font le lien avec
    PostgreSQL.
  - Aucune table de l'application de base n'est modifiée : toutes les tables du
    module sont préfixées gi_ (get-injs). L'intégration se fait par clés
    étrangères logiques (formation, groupe, étudiant) et par API.

Flux applicatif :
  Utilisateur → page Next.js → route API → service d'orchestration
              → domaine (moteur / parseur) → PostgreSQL → réponse JSON
              → revalidation de la page (router.refresh) → grille à jour.

5. MODELE DE DONNEES

Toutes les tables sont préfixées gi_ et possèdent des index sur les colonnes de
filtrage (formation, semestre, groupe, salle).

gi_academic_years
  id, code (unique), label, date_debut, date_fin, statut, active
  Année de référence : 2026-2027 (active = true).

gi_filieres
  id, code (unique), nom, ecole, actif
  STAPS (ENSEPS), STASE (ENSEP).

gi_formations
  id, filiere_id → gi_filieres, code (unique), nom, cycle, maquette, actif
  EM, ES, MS, APA, AND, LOI, ECJP, GER.

gi_batiments
  id, code (unique), nom, zone
  BP1, BP2, AMP, CNMS, CNSHN, GYM, EXT, NUM, CONF.

gi_salles
  id, batiment_id, code (unique), nom, type, capacite, equipements,
  schedulable
  type ∈ amphi | cours | td | lab | gym | terrain | dojo | piscine | conference.

gi_vagues
  id, code, label, niveau, annee_id, date_debut, date_fin, statut,
  effectif_prevu, effectif_reel
  Contrainte unique (code, annee_id). Une vague = une promotion recrutée.

gi_groupes
  id, code, label, formation_id, vague_id, annee_id, niveau,
  effectif_cible, effectif, source, actif
  Contrainte unique (code, annee_id). source ∈ referentiel | import.

gi_enseignants
  id, matricule (unique), nom, prenom, grade, specialite, email,
  max_heures, actif.

gi_modules
  id, code (unique), formation_id, semestre (1..10), titre, ects, nature,
  heures_cm, heures_td, heures_tp, room_need_cm, room_need_td,
  room_need_tp, source, actif.

gi_module_enseignants
  id, module_id, enseignant_id, type_seance (CM/TD/TP), charge_horaire
  Unique (module_id, enseignant_id, type_seance).

gi_etudiants
  id, matricule (unique), nom, prenom, sexe, date_naissance, email,
  telephone, annee_id, formation_id, groupe_id, vague_id, niveau, statut,
  source, importe_le.

gi_inscriptions
  id, etudiant_id, annee_id, filiere_id, formation_id, groupe_id, vague_id,
  niveau, semestre, statut, source, created_at
  Unique (etudiant_id, annee_id, semestre) : idempotence des imports.

gi_emplois_du_temps
  id, code (unique), libelle, annee_id, version, statut (brouillon|publie),

gi_seances

gi_generation_runs
  id, annee_id, edt_id, scope JSONB, options JSONB, statut, stats JSONB,

gi_import_jobs

gi_app_meta
  key (PK), value, updated_at — marqueur d'initialisation get_injs_seed_v1.

6. REGLES METIER LMD ET CONTRAINTES INJS
================================================================================

R1. Parcours = filière (mention) + formation (parcours) + niveau + groupe +
    vague + semestre + année académique.
R2. Niveau → semestres : L1 = S1/S2, L2 = S3/S4, L3 = S5/S6, M1 = S7/S8,
    M2 = S9/S10.
R3. Une année académique comporte les deux semestres de chaque niveau.
R4. Cours magistral (CM) mutualisé à l'échelle de la promotion, puis découpé
    en lots si l'effectif cumulé dépasse la capacité de la plus grande salle
    compatible.
R5. Travaux dirigés (TD) et travaux pratiques (TP) organisés par groupe.
R6. Une salle ne peut accueillir qu'une séance par créneau et par semestre
    (les semestres impairs et pairs ne se chevauchant pas, leurs grilles sont
    indépendantes).
R7. Un enseignant ne peut pas assurer deux séances au même créneau.
R8. Un groupe ne peut pas suivre deux séances au même créneau.
R9. La capacité de la salle doit être ≥ effectif du groupe (CM : effectif du
    lot). En l'absence de salle suffisante, la plus grande salle compatible du
    type visé est retenue et une alerte est journalisée. Si aucune salle ne suffit, la plus grande salle disponible du type
    visé est retenue et une alerte est journalisée.
R10. Quota hebdomadaire par groupe : 30 séances par défaut (paramétrable
    10..36) pour éviter les semaines saturées.
R11. Créneaux : P1 07:30-09:30, P2 09:45-11:45, P3 12:00-14:00 (pénalité 5),
    P4 14:00-16:00, P5 16:15-18:15, P6 18:15-20:15 (pénalité 3). Samedi :
    P1 et P2 uniquement. Soit 32 créneaux hebdomadaires, 27 si la pause
    méridienne est exclue (« éviter la pause méridienne »).
R12. Équilibrage : les séances sont réparties sur la semaine (pénalité de
    créneau + charge du jour + bruit déterministe).
R13. Type de salle privilégié par besoin :
    amphi → amphi > conference > cours
    td → td > cours > conference
    lab → lab > td > cours
    gym → gym > dojo > terrain
    terrain → terrain > gym
    dojo → dojo > gym
    piscine → piscine > gym.
R14. La grille hebdomadaire type porte une séance récurrente par type et
    par module : CM si heures_cm > 0, TD si heures_td > 0, TP si heures_tp > 0
    (limités aux 4 modules les plus pratiques par groupe). Les volumes
    complémentaires relèvent des semaines d'approfondissement et ne sont pas
    dédoublés dans la grille de base.
R15. Le moteur est déterministe : à périmètre et graine identiques, la grille
    produite est identique (hash FNV-1a sur code module + groupe + graine).

7. ALGORITHME DE GENERATION (PSEUDO-CODE)
================================================================================

ENTREE : annees, groupes(niveau, effectif, semestres), modules(semestre,
         volumes, besoin salle), salles(capacite, type), enseignants,
         affectations, creneaux, options
SORTIE : seances[], stats, alertes, nonPlacees[]

construire creneaux éligibles (samedi, pause méridienne)
indexer salles par type (tri capacité croissante)
indexer enseignants par module/type et par spécialité
initialiser occupations par semestre : salle / enseignant / groupe
initialiser chargeGroupe, chargeJour

POUR CHAQUE semestre DANS options.semestres :
  groupes_semestre ← groupes dont semestres contient semestre
  POUR CHAQUE formation DES groupes_semestre :
    modules ← maquette(formation, semestre)
    # 1. Cours magistraux mutualisés
    POUR CHAQUE module DES modules :
      lots ← partitionner(groupes_formation, capacité max salle CM)
      POUR CHAQUE lot :
        placer(type=CM, groupes=lot, besoin=room_need_cm,
               effectif=somme(effectifs))
    # 2. TD puis TP par groupe
    POUR CHAQUE groupe :
      POUR CHAQUE module : placer(type=TD, groupes=[groupe], quota=true)
      POUR CHAQUE module : placer(type=TP, groupes=[groupe], quota=true)

FONCTION placer(type, groupes, besoin, effectif) :
  SI quota atteint POUR un groupe → nonPlacees += raison ; RETOURNER faux
  POUR CHAQUE creneau TRIE PAR (pénalité, charge du jour, bruit) :
    SI un groupe est déjà occupé → CONTINUER
    salle ← meilleure salle disponible compatible (capacité ≥ effectif)
    SI aucune salle → CONTINUER
    enseignant ← premier enseignant affecté disponible (CM/TD/TP puis CM
                 puis spécialité)
    SI aucun enseignant → CONTINUER
    créer la séance et marquer les occupations salle / enseignant / groupe
    mettre à jour chargeGroupe et chargeJour
    RETOURNER vrai
  nonPlacees += « aucun créneau compatible » ; RETOURNER faux

FIN POUR
verifierConflits(seances)  # contrôle indépendant salle / enseignant / groupe
calculer statistiques (couverture, occupation, par semestre, places)
RETOURNER résultat

8. IMPORT EXTERNE D'INSCRITS (SITUATION 2)
================================================================================

8.1 Formats acceptés
  - CSV (séparateur ; , ou tabulation, détection automatique, BOM géré) ;
  - XLSX / XLS (première feuille du classeur) ;
  - taille maximale 15 Mo, 20 000 lignes par import.

8.2 Colonnes reconnues (alias insensibles aux accents, à la casse et aux
    caractères spéciaux) :
  matricule : matricule, code_etudiant, numero, id, no
  nom : nom, nom_de_famille, lastname, noms
  prenom : prenom, prenoms, firstname
  sexe : sexe, genre, sex, gender
  date_naissance : date_naissance, ddn, dateofbirth
  email : email, mail, courriel
  telephone : telephone, tel, phone, contact
  filiere : filiere, mention, ecole, departement
  formation : formation, parcours, specialite, programme, option
  niveau : niveau, level, classe, annee_etude
  groupe : groupe, group, grp
  vague : vague, promotion, cohorte, session
  semestre : semestre, semester, sem
  statut : statut, status, etat
  annee_academique : annee_academique, annee, annee_scolaire

8.3 Traitements
  1) lecture du fichier (CSV ou XLSX) ;
  2) normalisation des en-têtes et détection des colonnes (les colonnes
     inconnues sont tracées et ignorées) ;
  3) normalisation du niveau (L1/Licence 1/1 → L1, etc.) et du semestre ;
  4) résolution ou création de la filière, de la formation, de la vague et du
     groupe (si autoCreer = true) ;
  5) création d'une maquette LMD par défaut de 8 modules par semestre pour
     toute formation nouvelle (CM/TD/TP, besoins de salle) ;
  6) insertion des étudiants avec ON CONFLICT DO NOTHING sur le matricule ;
  7) insertion des inscriptions (deux semestres du niveau) avec ON CONFLICT
     DO NOTHING sur (etudiant, annee, semestre) ;
  8) recalcul des effectifs des groupes et des vagues ;
  9) génération optionnelle des emplois du temps du périmètre ;
  10) journalisation complète dans gi_import_jobs.

8.4 Garanties
  - idempotence : réimporter le même fichier ne duplique rien ;
  - traçabilité : chaque ligne en erreur est listée avec son numéro ;
  - résilience : une ligne invalide n'interrompt pas l'import ;
  - repreneur : les étudiants déjà présents dans la base de référence
    conservent leurs données, seules les inscriptions manquantes sont créées.

10. PROCEDURE D'IMPLEMENTATION PAS A PAS (COMMANDES)
================================================================================

10.1 Prérequis
  - Node.js ≥ 20 (testé avec Node 22)
  - PostgreSQL ≥ 14 (testé PostgreSQL 16)
  - npm ≥ 10

10.2 Installation
  cd backend-injs2026
  npm install
  npm install xlsx

10.3 Variables d'environnement (.env à la racine)
  DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:5432/app_db

10.4 Création des tables
  npx drizzle-kit push
  # ou génération de migration :
  npx drizzle-kit generate
  npx drizzle-kit migrate

10.5 Compilation et démarrage
  npm run build
  npm run start -- -p 3000
  # développement :
  npm run dev

10.6 Initialisation du référentiel INJS + cohorte de démonstration
  curl -s -X POST http://localhost:3000/api/seed | jq
  # attendu : 3474 étudiants, 100 groupes, 100 salles, 658 modules,
  #           136 enseignants, 2 filières, 8 formations, 5 vagues.

10.7 Génération complète de l'année académique
  curl -s -X POST http://localhost:3000/api/generation \
    -H "Content-Type: application/json" \
    -d '{"anneeCode":"2026-2027","inclureSamedi":true,"eviterPauseMidi":true}'

10.8 Génération ciblée (exemple : STAPS, formation EM, niveau L1, S1)
  curl -s -X POST http://localhost:3000/api/generation \
    -H "Content-Type: application/json" \
    -d '{"anneeCode":"2026-2027","filiereCode":"STAPS","formationId":1,"niveau":"L1","semestre":1}'

10.9 Import externe (scénario 2)
  curl -s -X POST http://localhost:3000/api/import \
    -F "fichier=@get-injs-app/data/exemple-etudiants-injs.csv" \
    -F "anneeCode=2026-2027" \
    -F "autoCreer=true" \
    -F "generer=true"

10.10 Export et impression
  curl -L "http://localhost:3000/api/emplois-du-temps/export?anneeCode=2026-2027&semestre=1" \
    -o emplois-du-temps-s1.csv

10.11 Validation technique complète
  npx next typegen
  npm exec tsc -- --noEmit --pretty false
  npm run build
  curl -s http://localhost:3000/api/health

10.12 Remise à zéro sélective du module
  psql "$DATABASE_URL" -c "truncate table gi_import_jobs, gi_generation_runs, gi_seances, gi_emplois_du_temps restart identity cascade;"
  # pour tout réinitialiser :

11. BLOCAGES RENCONTRES ET SOLUTIONS APPLIQUEES
================================================================================

B1. Socle imposé Next.js alors que la cible est Django + Flutter.
    → Architecture en couches équivalente (domaine pur, API, UI), documentée au
      §3. Le moteur et le parseur sont portables tels quels en Python/Flutter
      si nécessaire (algorithmes et contrats identiques).

B2. Référentiels partiellement publiés (maquettes ES incomplètes, formations
    STASE sans maquette).
    → Canevas LMD paramétrable de 8 modules/semestre, source tracée
      « canevas_parametrable_lmd_injs », volumes et besoins de salle explicites.

B3. Cohérence des effectifs : les groupes source portent un effectif cible mais
    la base est vide.
    → Seed d'une cohorte déterministe alignée sur l'effectif cible (3 474),
      puis recalcul systématique des effectifs réels après seed et import.

B4. Volume de séances et capacité des salles.
    → Les grilles sont isolées par semestre (périodes disjointes), mutualisation
      des CM, une séance récurrente par type, quotas par groupe, meilleur
      ajustement de capacité, alerte de saturation et rapport de couverture.
      Résultat de référence : 3 387 séances, 0 conflit, 99,9 % de couverture
      (4 TP non placés sur un semestre à 12 modules).

B5. Concurrence d'initialisation (double requête au premier chargement).
    → Verrou consultatif PostgreSQL (pg_advisory_xact_lock) + marqueur
      gi_app_meta et mémoïsation de la promesse de seed côté processus.

B6. Imports volumineux (14 000 lignes).
    → Traitement par lots (500 étudiants, 800 inscriptions), caches mémoire des
      référentiels, insertion en masse avec ON CONFLICT DO NOTHING, limitation
      à 20 000 lignes par fichier et 15 Mo.

B7. Fichiers hétérogènes (accents, séparateurs, colonnes nommées différemment).
    → Parseur tolérant : détection du séparateur, BOM, alias normalisés, dates
      FR/ISO, niveaux « Licence 2 » → L2, matricule généré si absent.

B8. Conflits résiduels lors des tests.
    → Double contrôle : occupations en mémoire pendant le placement, puis
      vérification indépendante verifierConflits() avant persistance ; les
      conflits éventuels sont remontés dans les statistiques et l'interface.

B9. Risque de doublons de séances lors d'une regénération.
    → Suppression transactionnelle du périmètre (année + semestres +
      formations [+ groupe]) avant insertion, puis nettoyage des en-têtes
      d'EDT devenus vides.

B10. Perte de la documentation téléchargeable en production.
    → Fichier livré dans get-injs-app/ et servi par
      /api/artifacts/conception (inline ou download=1).

B11. Compilation TypeScript stricte (types JSONB, tableaux vides).
    → Typage explicite des colonnes jsonb via $type<...>(), types dédiés pour
      les stats et les rapports, assertions de type contrôlées.

B12. Initialisation de la base avant le premier build.
    → build_and_start pour amorcer l'environnement, puis drizzle-kit push,
      puis /api/seed, puis génération, puis validation complète.

16. JOURNAL DES DECISIONS
================================================================================

D1. Moteur pur et déterministe (graine) pour garantir reproductibilité et
    testabilité.
D2. Isolation par semestre dans le contrôle des conflits : les semestres ne se
    chevauchant pas, leurs grilles cohabitent sans conflit.
D3. CM mutualisés avec découpage par capacité d'amphithéâtre : realism INJS
    (promotions de 250 à 300 étudiants).
D4. Quotas par groupe et équilibrage par jour pour des grilles lisibles.
D5. Import tolérant avec reconstruction du parcours : réponse directe à la
    situation 2 (aucun parcours académique préalable).
D6. Idempotence par contraintes uniques et ON CONFLICT DO NOTHING.
D7. Documentation générée dans le dépôt et exposée par l'API pour rester
    téléchargeable en toutes circonstances.
D8. Aucune dépendance à un service externe : tout fonctionne hors ligne.
