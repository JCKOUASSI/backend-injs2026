# Audit du paquet GET INJS APP — recette isolée

**Conclusion : paquet cohérent pour essais locaux ; NON prêt pour un déploiement institutionnel.** Périmètre : archive de recette produite sur la branche courante, reconstituée sur une extraction jetable du commit déployé de référence `70d08dad1821caceb61b22fe22cf70e13155bf18`. Aucun accès au domaine public, à un VPS, à une base ou à des identifiants réels ; son état réel n'a pas été audité.

## Constats classés

| Niveau | Constat | Conséquence / action |
|---|---|---|
| **Bloquant production** | L'API v2 ne fonctionne qu'avec `DEBUG=True`, drapeau expérimental et année `BENCHMARK-*`. Le drapeau d'écriture n'est pas défini dans `config/settings.py` (défaut `False`) et la route frontend v2 est éliminée du build de production. | Le paquet **ne remplace pas** le moteur annuel visible à `/edt/generation-annuelle`. L'installer ne fournirait pas une « GET INJS APP institutionnelle » utilisable. Ne pas activer `DEBUG` pour la rendre visible. |
| **Bloquant production** | Pas d'attestation des volumes/calendrier ni des identités `Participant`, géolocalisation QR non validée ; le préflight refuse toute publication/badgeage v2. Les 779 propositions locales demeurent hypothétiques. | Obtenir pièces administratives et recette de bout en bout avant toute proposition d'activation ; aucune attestation ne peut être déduite des données fictives. |
| **Bloquant production** | Aucune comparaison avec le site réellement en service, ni essai de charge/rollback sur sa configuration cible ; pas de worker durable raccordé à l'écran. | Décision de déploiement impossible sur la seule preuve locale ; les tests PostgreSQL sur socket isolé ne couvrent pas l'exploitation ni le RSS système. |
| **Risque élevé** | L'activation conjointe `DEBUG=True` + drapeau expérimental dans une base non isolée permettrait d'écrire des séances **BENCHMARK** ; le nom de l'année n'est pas une garantie de séparation physique des bases. | Ne pas activer ces paramètres sur un site réel. Tester et renforcer la séparation de l'environnement avant tout pilote autorisé. Un test ajouté vérifie le refus quand `DEBUG=False`, même avec le drapeau activé. |
| **Risque de retour arrière** | `edts.0013` ajoute tables, index et contraintes ; sa marche arrière supprime les ajouts, donc peut détruire des données v2 après écriture. En exploitation, privilégier retour au code stable en laissant les ajouts de schéma ; plan de sauvegarde/restauration et durée de migration à vérifier hors de ce banc. |
| **Risque de traçabilité** | Les fichiers GET INJS de l'overlay ont été commités séparément, mais le SHA `commit_source` seul ne décrit ni le commit de référence à enrichir, ni la liste des 28 chemins sélectionnés. La branche conserve `scolarite.0021` non déployée et des modifications de volumes hors périmètre. | Conserver **commit de référence + archive + manifeste + empreintes SHA-256 ensemble** ; ne pas déployer toute la branche. Toute publication requiert une revue distincte et une décision explicite. |
| **Couverture partielle** | Les autres écritures directes ORM et outils administratifs ne sont pas protégés par une contrainte universelle de base ; certains écrans de supervision historiques lisent des statuts legacy. | Audit transversal et essais d'intégration réels avant interconnexion institutionnelle. Les gardes applicatives v2 ne sont pas une attestation de compatibilité totale. |

## Vérifications et correction de composition

- La première sélection du paquet avait recopié `annee.py`, `besoins_maquette.py` et `campagnes.py` depuis le working tree. Ces fichiers dépendaient de champs locaux `scolarite.0021` et **deux tests historiques échouaient** sur la référence isolée. Cette sélection a été **abandonnée** ; l'overlay final conserve les trois fichiers du commit de référence. Après correction : **109/109 tests API historiques** verts.
- Archive finale : **28 fichiers réguliers** de code/tests GET INJS, seuls chemins relatifs contrôlés, aucun chemin `backend/scolarite/`, aucune migration `scolarite.0021`, manifeste à SHA-256 par fichier ; `sha256sum -c SHA256SUMS.txt` vérifie l'archive et le manifeste. Deux constructions identiques ont donné le même SHA-256. Les fichiers de l'extraction reconstruite correspondent au manifeste.
- Extraction reconstruite : `manage.py check` et `makemigrations edts scolarite --check --dry-run` OK ; **110/110 tests QR/API/Présences sur SQLite**, y compris un nouveau test `DEBUG=False` + drapeau activé → API 403 et service sans écriture ; **81/81 tests QR/interop/Présences et concurrence sur PostgreSQL local isolé** avant cet ajout de test (pas de nouveau passage PostgreSQL de celui-ci). Build frontend et test BenchV2 OK ; le bundle conserve un avertissement de taille. Le build **ne contient pas** le chemin `/edt/bench-v2` ni son libellé.
- `edts.0013` : uniquement `CreateModel`, `AddField`, `AddIndex` et `AddConstraint` dans la migration ; application → retour `0012` → réapplication réussis **sur une base SQLite jetable vide**. Cela ne démontre ni le temps de verrouillage PostgreSQL réel, ni un rollback sûr après écriture.

**Décision recommandée :** accepter ce paquet uniquement comme objet de recette isolée. Refuser toute bascule du domaine ou activation du moteur v2 tant que les constats bloquants ne sont pas levés et qu'un responsable n'a pas attesté les sources métier et QR. Ne pas transmettre de secret ou donnée nominative dans cette conversation.
